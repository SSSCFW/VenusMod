# pingと分けて確認するサービス監視

Minecraft1.21.1 / NeoForge。既存の定期監視を、仮想Web・DNS・転送・レッドストーン制御の入口へ拡張します。実ブラウザー、外部ソケット、OSコマンド、任意TCPポートのスキャンは使いません。

## 基本の設定

同じLANで監視Serverを192.168.1.10/24、Web Serverを192.168.1.20/24として配線します。Web側は `web on` を設定してください。監視Serverのコンソールでは、例えば次を実行します。

```text
monitor add host 192.168.1.20
monitor add site web 192.168.1.20
monitor interval 5
monitor thresholds 3 2
monitor on
monitor status
```

種類を省略した `host` は従来のICMP往復、`site` はTCP80とWebサービスの稼働確認です。本体が稼働していても `web off` ならhost=UP/site=DOWNになります。反対にACLでICMPだけ拒否すれば、host=DOWNでもsite=UPになり得ます。サービスの確認をpingの成功で代用しません。

間隔、連続失敗・復旧回数、UNKNOWN/UP/DOWN、監視元のPAUSED、処理上限による判定保留、状態変化だけのSyslog通知は従来機能を共用します。操作は機器GUIのコンソールから行い、「監視」ボタンで一覧を表示します。表示の更新は再クリック/再実行です。専用の監視設定フォームを追加したわけではありません。

## 監視種類

| 種類 | 例 | 確認内容 |
| --- | --- | --- |
| 種類省略、またはicmp | `monitor add host icmp 192.168.1.20` | 仮想ICMPの往復到達性 |
| web | `monitor add site web 192.168.1.20` | TCP80・受信機器がServer・web有効 |
| dns | `monitor add resolver dns 192.168.1.53` | UDP53・既存DNSサービス有効 |
| transfer | `monitor add files transfer 192.168.1.20` | TCP5000・既存の仮想転送受付への到達性 |
| control | `monitor add signal control 192.168.1.30` | TCP25570・受信機器がレッドストーン通信端末 |

宛先は数値のユニキャストIPv4です。ホスト名、IPv6、`http://`、URLパス、`tcp`のような任意プロトコル指定、1〜65535以外のポートを受け付けません。ICMPにはポートを指定しません。

**これらは既存の通信メタデータとサービス稼働条件の検査です。** 実TCPのSYN/ACK、接続再送、HTTP本文・ステータスコード、DNSの質問/回答内容の整合、負荷や内部処理能力は検査していません。DNSのUPは特定の名前が正しい回答を返す保証ではないため、その確認には `nslookup` を使ってください。転送のUPも大きなファイルの完走や所要時間を保証しません。

監視ではWeb画面やログ本文を取得せず、転送フローを開始せず、レッドストーン出力・機器設定を変更しません。制御端末の出力が11であれば、正常な監視によって11から変わりません。

## NATの公開ポート

ルーターで外側P1の8080番を、内側サーバーの80番へ転送する例:

```text
nat port 0 inside
nat port 1 outside
nat on
nat forward add 1 tcp 8080 192.168.1.20 80
```

外側IPが203.0.113.1の場合、監視Serverでは次を使います。

```text
monitor add site web 203.0.113.1:8080
```

**公開8080番と、実サービスの内部80番を区別**します。8080→内部81番の誤設定、Webを持たない機器への転送、`web off` はDOWNです。DNSはUDPの公開ポート→内部53、制御はTCPの公開ポート→内部25570という形でも利用できます。

送信先までのVLAN・経路・受信/送信ACL、変換後のポートと稼働状態、戻りの経路/ACLをすべて確認します。DNS監視もSyslogのような片方向配送ではなく、往復できることを条件にします。

停止・非対応サービス・誤内部ポート・応答失敗では、NATの新しい変換表を確定せず、既存エントリーの期限も延ばしません。成功した確認では通常の通信と同様にNAT表を利用/更新します。既存のNAT容量・期限上限はそのままです。

## 権限・保存・処理上限

監視対象の編集と結果閲覧は、監視Serverの既存メニュー認可を使います。`public on`は監視設定や監視一覧を公開する操作ではありません。対象サービスへの到達性を確認することと、そのWeb内容の閲覧・設定変更・レッドストーン操作権限を持つことは別です。監視のUPによって権限を取得できません。

設定のコピーを検証してから一括で反映します。重複した監視名を別種類で上書きせず、`monitor delete NAME`の後で登録し直します。削除・clearで種類の設定も消去し、同名をICMPとして再登録できます。監視だけの設定編集は既存転送・NAT表を消しません。

保存形式はv11です。従来のIPv4一覧と監視方針を維持し、監視名ごとの種類・公開ポートだけを追加保存します。旧v1〜v10を読み込み、既存対象はICMPのまま引き継ぎます。採掘した機器は装着品、故障、所有権も保持します。状態・統計・期限は従来どおり保存せず、再設置後はUNKNOWNです。古いMODへのダウングレードは保証しないため、更新前のバックアップを残してください。

全種類で**1台16対象、1ディメンション64監視元/256対象、1tick最大2対象**の同じ予算を使います。サービス種別ごとに別枠を用意して上限を回避させません。1対象1期限で、監視のためにチャンクをロードしません。処理上限で判定不能ならDOWNを通知せず保留します。

通信Payloadはnetwork-2を継続します。サーバーと参加クライアントは同じMOD版を利用してください。136種の細いカラーケーブル、4/16幅、テクスチャ、モデル、レシピ、ゴーグル、クリエイティブタブは変更していません。GUI/JEI共通ガイドは従来の監視4手順へサービス3手順を追加し、19トピック79手順です。

全ネットワーク仕様の完成ではありません。名前宛先監視、HTTPステータスコードの照合、DNS回答監視、任意TCP接続、SNMP、自動修理などは未対応です。

参考: RFC9293のTCPとRFC792のICMP。これは完全なワイヤ形式/状態機械の実装ではなく、両者の検査対象を分けるゲーム用モデルです。検証記録は [NETWORK_SERVICE_MONITOR_VERIFICATION.md](NETWORK_SERVICE_MONITOR_VERIFICATION.md) を参照してください。
