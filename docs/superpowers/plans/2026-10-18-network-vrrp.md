# VRRP広告・タイマー実装計画

> **For agentic workers:** Use superpowers:executing-plans. この承認済みネットワーク仕様の継続作業は同セッションで実装・検査・既存ブランチへのpushまで行う。

**Goal:** 優先度の即時比較だったVIP選出を、広告と期限でMaster/Backupが遷移するIPv4 VRRPへ置き換える。
**Architecture:** VrrpSettings（保存）、VrrpEngine（決定的なイベント状態機械）、VrrpSimulation（既存L2/VLAN/ACLとの接続）、VrrpCommands/Guide（操作説明）を分離する。実ソケットは使わない。
**Tech Stack:** Java21 / Minecraft1.21.1 / NeoForge21.1.235 / 任意Create6.0.10・JEI。
**Spec:** docs/NETWORK_SYSTEM_SPEC.md の故障・冗長化・保存・軽量化要件。プロトコルの基準はRFC9568、ゲーム時間へ丸める。IPv6・複数VIP/複数VRID同居・所有者優先度255・NAT状態同期は今回対象外。

## 制約と判断

- 既存 feature/venus-hostile-mobs と Build 1.21.1 NeoForge のみ。追加ブランチ/workflowなし。
- ケーブル8種の4/16幅・独自PNG74枚・モデル・レシピを変更しない。
- 既存vip/priorityは保持し、v5でポート(auto/0–5)、VRID(1–255)、広告間隔(1–10秒)、preempt、有効状態を追加。v1–v4は標準値で移行する。
- 既存 `vrrp IP PRIORITY` を維持。VIPのLANインターフェースは明示または一意に特定できるときだけ有効。設定の保存時にIPの変更を妨げず、不適合時はINITIALIZEと診断を出す。
- MasterだけがVIPのARP/データに応答。仮想MACを一定にする。同じLANの二重Masterを優先度で隠さず、通信を競合エラーにする。
- 正常な広告受信で期限更新、故障時はpriority0を送らず、管理者のoff時だけ送信。広告遮断・同優先度・preempt off/onを検査。
- 全体128参加機器、1機器64相手、4096配送イベント、64イベント/tick、変更時のL2探索は2機器/tick。期限イベントは機器ごとに1件、受信のたびに古い期限を積み増さない。
- 通常tickのみ時間を進め、状態閲覧やping連打はタイマーを進めない。設定変更時にも変更のない機器は状態を保持する。
- NATのセッション共有は行わない。切替時のARP/MAC/仮想転送は失効、切替とNAT状態引継ぎを混同しない。

## 重点レビュー

広告がVLAN/L3境界を越えないこと／分断時に隠れた全体選出で通信を通さないこと／offの広告と故障を区別すること／旧VIPが無言で他ポートへ移らないこと／NAT・OSPFを閲覧操作だけで再初期化しないこと。
