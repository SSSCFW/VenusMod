# ネットワーク初期実装 — 続行分

この変更は `dbb13f98efeab6521a9cbd726a0cd7620fdbbf25` の初期実装を修正・検証するものです。全体の [仕様書](NETWORK_SYSTEM_SPEC.md) にある全プロトコルの完成を意味しません。[初期版の使い方・制約](NETWORK_IMPLEMENTATION.md) も参照してください。

## 修正した通信の振る舞い

- 固定速度が10Mbpsと100Mbpsのように食い違うリンクはLink Downになります。片側Autoなら、両端の装着モジュールとケーブルが対応する固定速度に合わせます。
- 高速モジュールを抜いても希望する固定速度設定は保存します。ただし対応できなくなったリンクは停止し、再装着またはAutoへの変更で復旧します。指定速度を黙って書き換えません。
- ルーターはARP要求を受けた側のインターフェースで応答します。他のLANのアドレスへ暗黙のProxy ARPを行いません。正しいゲートウェイ経由のIP通信とは区別します。
- 簡易DHCPは仮想ゲートウェイのVIPを貸出候補から除外します。
- 表示用のMACアドレスはJavaの32bit `String.hashCode()`ではなく機器IDのSHA-256から生成し、機器ごとにキャッシュします。既知の文字列ハッシュ衝突によるMAC重複を避けます。完全なMACレジストリによる衝突解決を実装したという意味ではありません。

## 処理上限

| 対象 | 上限・動作 |
| --- | --- |
| 通信探索 | 1要求全体で8,192作業単位。pingは往復で共通の予算を使う |
| 保持する経路 | 最大64機器 |
| 待ち行列 | 8,192件以下 |
| VLAN種類数 | 1ディメンションで128種類 |
| 簡略スパニングツリーの計算 | 262,144組以下 |
| GUI/CLI要求 | 1ディメンションで4件/tick、同一プレイヤーで2件/tick |

上限を超えたときは、保護を無効化したり、途中までの探索結果を成功として返したりせず、上限エラーとして通信を停止します。画面の開き直しでもプレイヤー別の要求予算はリセットされません。拒否したプレイヤーIDは無制限に保存しません。

これらは負荷の上限を設けるための値であり、任意のサーバー構成でTPS低下が絶対に起きないという保証ではありません。大規模マルチプレイでの負荷計測は未実施です。

## ケーブルとテクスチャ

初期版の4/16幅の芯・接続腕と独自テクスチャを維持しています。衝突・選択形状も同じ細さです。全ケーブル状態の非遮蔽検査に加えて、全8種類の機器・全状態が隣接面を隠さないことをGameTestに追加しました。

生成アセットは初期版と同じ174 JSON・74 PNGです。手動のクライアント画面、JEI表示、シェーダーと組み合わせた描画は、この自動検査とは別に確認が必要です。

## 検証記録

ローカルJava 21で、不具合を再現する新規回帰テストを先に実行し、7ケースの失敗を確認してから修正しました。

- `NetworkContinuationTest`: 28アサーション成功。過大VLAN、長い経路、固定速度不一致、モジュール抜去、MACの既知衝突、ARPインターフェース、DHCP/VIP、VLAN分離、帯域共有を検査。
- `NetworkRequestBudgetTest`: 10,009アサーション成功。このうち10,000回は要求上限到達後の拒否を確認する反復検査です。
- `NetworkWiringGameTests`: 実ブロックでの接続→T字分岐拒否→撤去後復旧→断線、光モジュールの装着/抜去/再装着、機器の非遮蔽を追加。論理Linkを手で注入せず、通常のロード・tickイベントによる登録と配線解析を使います。
