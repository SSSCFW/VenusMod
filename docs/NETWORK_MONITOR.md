# 定期的な死活監視と障害・復旧通知

既存ネットワークサーバーを監視元にし、指定した仮想IPv4へ定期的にICMPの往復確認を行います。停止した機器自身のログが送れない場合も、別の監視サーバーから応答の消失を観測できます。実際のpingプロセス、OSソケット、外部インターネットは使用しません。

## 設定と使い方

```text
監視Server 192.168.1.10 ─ L2SW ─ 対象 192.168.1.20
```

端末は同じ/24として、スイッチの別ポートへそれぞれ独立したケーブル区間を接続します。遠いサブネットを監視する場合はゲートウェイと戻りの経路を用意します。

監視するネットワークサーバーのGUIコンソール:

```text
ip 192.168.1.10/24
monitor add base 192.168.1.20
monitor interval 5
monitor thresholds 3 2
monitor on
monitor status
```

`interval`は秒、`thresholds`は連続失敗回数・連続成功回数の順です。既定は5秒間隔、3回失敗でDOWN、2回成功でUPです。通常のサーバーtickで進み、20tickを1秒として扱います。TPS低下や監視件数に応じて実時間の間隔は伸びます。

監視機器GUI上部の「監視」ボタン、または`monitor status` / `monitor list`で、対象別の状態・確認回数・連続回数・最終確認tick・計算上のRTT・直近の診断を表示します。表示内容は再クリック/再実行で更新します。新しい専用フォームはなく、設定変更はCLIです。

```text
monitor delete base
monitor off
monitor clear
monitor help
```

`delete`は指定対象を削除、`clear`は全対象を削除してOFF、`off`は設定した対象を残して停止します。最後の対象を削除した場合もOFFになります。重複した監視名で既存のIPを上書きせず、削除後に再登録します。監視名は英数字・_・-の1〜24文字、宛先は数値のユニキャストIPv4です。DNS名・IPv6・ブロードキャスト/マルチキャスト監視は今回含みません。

## 状態と誤判定を避けるルール

- 初期UNKNOWN。登録/有効化だけではUPにせず、指定回数の確認後に判定します。
- 成功すると連続失敗回数を0、失敗すると連続成功回数を0へ戻します。
- DOWNは「この監視元からICMPの応答を得られない」という意味です。対象の本体故障だけでなく、ACL・VLAN・断線・返信経路なし・収束待ちでも起こります。
- 監視元自身の故障中はPAUSEDを表示し、対象の最終確定状態を維持します。監視元の復旧後は連続回数をリセットして再確認します。監視元がアンロードされた場合はランタイムから撤去され、再ロード後にUNKNOWNから始まります。
- シミュレーターの探索/経路長/VLAN計算上限で判定できない場合は、DOWNと通知せず「判定保留(処理上限)」として理由を表示します。最終確定状態は保持し、連続回数はリセットします。
- OFFへの変更や監視条件の変更は観測状態を再作成します。同じ設定の再適用、別物理網の配線編集、Syslog等の別設定変更では監視時計をリセットしません。

この版は既存の仮想ICMP往復経路の検査を定期実行するものです。実パケットのシーケンス・独立したタイムアウト待機・再送を新たにエミュレートする機能ではありません。RTTはモデルの計算値で、実サーバーの実時間測定ではありません。Webだけの停止やTCPサービスの故障まではICMPで検出できません。

## 状態変化のログとSyslog

UNKNOWNから最初にUP/DOWNへ確定した時も含め、状態が変化した時だけ次の形式で通常の`log`へ記録します。

```text
MONITOR DOWN base 192.168.1.20 (UP → DOWN): 診断理由
MONITOR UP base 192.168.1.20 (DOWN → UP): 応答情報
```

DOWNの重大度は3(error)、UPは5(notice)。平常時の毎回の確認や、DOWNの継続だけでログを増殖させません。これらの通知を別のSyslogサーバーへ集めるには、監視元で設定します。

```text
syslog target 192.168.1.30
syslog level 6
syslog on
```

Syslog受信側にも`syslog server on`、配線・IP・必要なフィルター設定が必要です。通知の配送は通常のSyslogに従い、配送不能なら届きません。監視サーバー自身も停止していれば通知できないため、重要な網では監視元も別系統に用意してください。

## NAT・ACL・マルチプレイ

確認要求と返信は既存のVLAN・経路・NAT・入出ACLを通ります。pingだけ許可しない設定なら、Webが動いていてもDOWNです。NATの外側IPを監視しても内側サービスの健康状態を証明しません。

監視の開始/編集/停止と観測結果の閲覧は、既存の機器メニューの所有者・共有者・距離などの認可を使います。`public on`は監視の一覧や編集権限を公開する操作ではありません。監視は装置の遠隔設定を書き換えず、仮想ICMPの確認のみを行います。

監視設定だけの編集では既存の大容量転送・NAT表・動的経路を消去しません。不正な入力は設定コピーの検証で拒否し、一部だけ反映しません。GUIの通信形式は既存network-2を継続します。

## 保存と処理上限

保存形式はv10です。ON/OFF、監視名とIPv4、間隔、失敗/復旧閾値を、機器の装着品・故障・所有権と一緒に保持します。v1〜v9の機器は監視OFFで読み込みます。観測状態・統計・時計・期限は保存しません。古いMODへのダウングレードは保証しないため更新前のワールドバックアップを保持してください。

1台16対象、全体64監視サーバー/256対象、1回のサーバーtickに最大2対象を処理します。失敗中の監視元に対する期限確認もこの2件に含め、無制限に処理しません。各対象が持つ期限は1件だけで、過去の未処理分を一括実行しません。対象が多い場合は予定時刻順に処理し、実際の確認周期が延びます。

上限に達した新規設定は拒否し、稼働中の他の監視を止めません。保存済みの機器をロードして上限を超えた場合も設定は保持し、当該機器だけLIMIT表示で休止します。容量が空いた後に`monitor on`を再実行すると再登録します。これはTPSの保証値ではなく、処理回数・メモリの上限です。

既存136種類の無染色/16色ケーブル、4/16幅、画像、モデル、レシピ、専用タブは変更していません。GUI/JEI共通ガイドへ既存アイコンを使った4手順を追加しました。監視はSNMPや実TCP監視・自動修理・自動フェイルオーバー・NTPの実装ではありません。
