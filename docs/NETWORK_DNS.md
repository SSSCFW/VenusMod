# 名前で設備へ接続 — DNS・TTL・ラウンドロビン

Minecraft 1.21.1 / NeoForge。承認済みの [全体仕様](NETWORK_SYSTEM_SPEC.md) のDNSを拡張します。**ゲーム内のIPv4 Aレコードだけ**を扱い、外部DNS・ソケット・Webブラウザーには接続しません。Create/JEIは任意です。

## 基本の構成

```text
PC 192.168.1.10 ─ L2SW ─ DNS 192.168.1.53
                  └──── Web 192.168.1.20
```

各端末は/24、異なるポートから独立したケーブル区間で接続します。途中のT字分岐は使いません。DNSは既存のネットワークサーバー、ルーター、L3スイッチで動作します。新しい筐体やテクスチャは不要です。

DNS側:

```text
ip 192.168.1.53/24
dns-record base.local 192.168.1.20
dns-server on
```

Web側は `ip 192.168.1.20/24` と `web on`。PC側:

```text
ip 192.168.1.10/24
dns 192.168.1.53
nslookup base.local
ping base.local
open base.local
transfer base.local 100
```

`transfer`は仮想100MBで、実ファイルを生成する操作ではありません。`trace 名前`、`redstone 名前 15`、`open 名前:8080`のような宛先も使えます。レッドストーンの宛先は対応する通信端末が必要です。

IP直指定は従来どおり使え、DNS問い合わせを発生させません。`http://`付きURI、パス、クエリー文字列、外部画像、IPv6形式は受け付けません。数値とドットだけの壊れたIPv4を名前へ読み替えることもありません。

## TTLとキャッシュ

旧来の `dns-record NAME IP` は互換維持し、TTLは既定60秒です。任意のTTLを秒単位で指定する場合:

```text
dns-record set base.local 10 192.168.1.20
dns-record ttl base.local 30
dns-record list
```

アプリケーションによる名前の利用は機器ごとのキャッシュを使います。**DNS側のレコードを変更しても、既存クライアントのキャッシュは満了まで変わりません。** キャッシュヒットや画面の閲覧で期限は延長しません。サーバーのゲームtickで進み、20tick=1秒です。実時間はTPSの影響を受けます。

```text
dns-cache
dns-cache clear
```

上記は自機だけの確認・消去です。キャッシュ中ならDNSサーバーの停止中も回答を利用できますが、宛先への実際の通信が成功する保証ではありません。TTL満了後は再問い合わせを行い、失敗しても古い回答を使い続けません。

IP/GW/DNSサーバーや自機のVLAN等のネットワーク設定変更、機器削除・再配置では自機のキャッシュをクリアします。物理リンクの切断だけでは名前回答を捨てず、解決後の実経路で通信断を判断します。別の端末・別物理網で同じDNSサーバーIPとホスト名を使っても、クライアントIDごとに分離します。

DNSレコード・TTL・サービス状態だけの編集は経路変更として扱わず、既存の転送やNAT変換表を消去しません。設定の保存はサーバー側で行います。

## 複数Aレコードとラウンドロビン

```text
dns-record set pool.local 0 192.168.1.20 192.168.1.21
```

1名に最大8個のIPを登録できます。成功した直接問い合わせごとに回答リストの先頭を順番に回します。1回の回答には全IPを含み、アプリは最初のIPを使用します。TTL0はキャッシュしないため、連続操作で回答順の変化を観察できます。

TTLを10秒にした場合は、受け取った回答リストと順序を10秒間保持します。キャッシュヒットだけでは権威側の順序を進めません。

**ラウンドロビンは死活監視でも自動フェイルオーバーでもありません。** 故障中のIPも設定どおり返し、最初のIPが失敗しても勝手に他のIPを試しません。完全な負荷分散装置を実装した意味ではありません。

## 診断と否定応答

```text
nslookup base.local
nslookup base.local 192.168.1.53
dns-negative-ttl 10
dns-record delete base.local
dns-server off
```

`nslookup`は**毎回直接問い合わせる診断**です。アプリキャッシュを読み書きせず、キャッシュ中の古い回答とDNS側の最新情報の違いを確認できます。第2引数は数値の仮想DNSサーバーIPです。

DNSから実際に「その名前がない」という応答を受けた場合だけ、NXDOMAINとして既定10秒保存します。名前を後から登録しても、そのクライアントの否定TTL満了または `dns-cache clear` まで残ります。否定TTLは0〜300秒で、0は保存しません。

**断線、UDP53のACL拒否、応答経路の欠落、DNSサービス停止はNXDOMAINではありません。** この版ではこれらの失敗をキャッシュせず、次回操作で再問い合わせます。SOA付きの実ワイヤ形式を扱わないため、否定TTLはDNS機器の設定値を使用するゲーム用モデルです。

## ACL・NAT・権限との関係

問い合わせは既存のUDP53の仮想通信で、L2/VLAN、ルーティング、NAT、入出ACLと戻りの経路を検査します。DNS用にpingを代用しないので、ICMPが拒否されていてもUDP53が許可されていれば名前解決できます。

既存NATでUDP53→内部DNSの53番へ転送する構成にも対応します。53→54のような誤った転送や、サービスが停止している宛先への問い合わせは成功扱いにせず、新たなNATエントリーを確定しません。NXDOMAINは有効なDNS応答なので、その通信自体のNATエントリーは通常どおり作成されます。

名前が分かっても、その後のWeb/TCP80、仮想転送/TCP5000、レッドストーン/TCP25570等はそれぞれのポートと経路・ACLを再検査します。ポート転送先のサービスポートも確認します。**DNSは機器の操作権限を与えません。** Web/制御機器の所有権・共有・公開設定は従来どおりサーバー側で確認します。

DNSの回答自体はUDP53へ到達できる機器が取得できます。DNSレコードに秘密情報を置くアクセス制御ではありません。DNS設定の変更には機器の管理権限が必要です。

## 保存・処理上限・互換性

保存形式はv8です。Aレコード、追加IP、TTL、否定TTL、有効状態を機器アイテムへ保存し、装着モジュール・故障・所有権の保持は従来どおりです。**動的キャッシュ、残り期限、ラウンドロビンの現在位置は保存しません。** v1〜v7を読み込み、旧単一レコードは既定TTL60秒で利用できます。旧版で保存できた特殊な名前も勝手に削除しませんが、新しい名前の形式に適合しない場合は一覧に要修正と表示し、削除・再登録できます。

名前は大小文字と末尾1個のドットを正規化します。ASCIIの名前は合計64文字まで、1ラベル63文字までです。下線は旧版との互換のため認めます。IP/GW/ピア等の機器設定そのものをホスト名で指定する拡張ではありません。

キャッシュは1機器64名・全体4096名、権威側の回転位置は全体2048名までです。1レコード1期限のまま更新し、毎回のキャッシュ参照でタイマーを増やしません。期限切れ回収は1tick最大32件、回収待ちでも期限が切れた回答は利用しません。満杯の場合は古いキャッシュから退避し、権威設定自体を消去しません。正TTLは0〜86400秒です。

旧MODへ戻す互換性は保証しません。更新前のワールドバックアップを保持してください。

GUI/JEIのDNS接続図5手順を追加し、全体16トピック63手順です。8種類のケーブルの4/16幅、独自PNG74枚、モデル、レシピは変更していません。

## 今回の範囲

平坦なAレコード表、正/否定TTL、機器キャッシュ、回答順の回転、数値IPまたは名前による既存設備への接続です。AAAA/IPv6、CNAME/PTR/SRV、再帰・委譲・複数ゾーン、DNSSEC、mDNS、実DNS形式、TCPフォールバック、死活監視付き負荷分散は未対応です。`.local`もこのMODでは通常の仮想名としてのみ扱います。

設計参考: [RFC 1035](https://www.rfc-editor.org/rfc/rfc1035.html) のTTL、[RFC 2308](https://www.rfc-editor.org/rfc/rfc2308.html) の否定応答キャッシュ。RFC準拠の全DNSスタックを実装した扱いにはしません。検証は [NETWORK_DNS_VERIFICATION.md](NETWORK_DNS_VERIFICATION.md) を参照してください。
