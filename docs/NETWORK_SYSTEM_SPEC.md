# VenusMod ネットワークインフラ仕様書

> 設計版 **v0.1 / 2026-10-17** — **未実装**。本書の数値・ゲームバランス・機器仕様のうち「暫定」と示す項目は実装・テスト時に再調整する。  
> 対象: **Minecraft 1.21.1 / NeoForge 21.1.x / Java 21**  
> 作業ブランチ: `feature/venus-hostile-mobs`  
> Createとは**独立**。JEIは**任意連携**。既存機能・レシピ・ワールドを仕様書追加だけで変更しない。

## 1. コンセプト・確定方針

LAN・光ファイバー・L2/L3スイッチ・ルーター・ONU・OLT・PC・サーバー等を設置し、現実のネットワークを参考にした構成をMinecraft内で構築する。Javaで仮想ネットワークをシミュレーションし、経路・VLAN・機器設定・故障に応じて通信の成否を変える。ネットワークスペシャリスト相当の知識を活用できるようにしつつ、**ゲーム性とマルチプレイでの軽さを優先**する。

- Minecraft専用サーバーが通信状態・設定・所有権・故障・転送速度を管理する**サーバー権威型**。
- **実ブラウザー、実インターネット、現実のLAN、OSソケット、外部HTTP接続は使わない**。ゲーム内Web風画面やIPアドレスは完全に仮想。
- JavaでEthernet/ARP/IP/VLAN/ルーティング等を表現し、必要な制御パケットの状態遷移を再現。大容量ファイル等は仮想バイト数と帯域・待ち時間で集約し、実パケットを大量生成しない。
- ネットワークスペシャリスト専用の「学習モード」は追加しない。代わりに**各機器のGUIおよびJEI内に詳細ガイド・構成例**を表示。
- 機器にランダム故障を導入し、修理・冗長化（VRRP、STP/RSTP等）を有用にする。高価な**完全安定化モジュールで内部ランダム故障率を0%**にできる。
- 高速なケーブル・ポート・仮想ISP/WAN回線ほど**非線形に高コスト化**。金を多量に使い、上位にダイヤモンド/ネザライト/ネザースター/既存の金星素材を使う。
- **各ポート**に速度設定と専用アップグレードを持たせ、機器全体の処理容量も独立した性能値にする。
- 機器の採掘→アイテム化→再設置で**すべての永続設定、スロット内容、強化、所有権、故障状態**を引き継ぐ。
- Createの有無に依存せず基本機能が動き、将来的なCreate連携は別の任意アダプターに限る。

## 2. 配線・物理トポロジー

### 2.1 接続ルール

- ケーブルは設置できるブロック。銅線LANと光ファイバーは物理媒体が異なり、対応する機器ポートや光トランシーバーが必要。
- Ethernetケーブル途中の**T字分岐だけでは**3台を接続できず、L2スイッチ等を経由する。PON光スプリッタは別の規則で扱う。
- 機器は1～2ブロックでも複数の論理ポートを持てる。配置時または接続時にポートを選択し、端点の対応規格、配線長、接続相手をサーバーで検査する。
- ケーブルの経路情報から**端点と規格・長さ・損傷状態を持つ論理リンク**を作る。配線が壊れたときは影響範囲だけ再計算する。
- 接続距離・ケーブル種別・速度が不適切ならリンクは不成立／低速となる。配線ダクト・パッチパネルの多条収容は追加候補。
- 光Ethernetのポイントツーポイント接続ではONU/OLTは不要。**PON構成**はOLT→受動スプリッタ→ONUの専用回線。
- ディメンション間に通常ケーブルを直接通せず、金星の**惑星間通信装置**が必要（後期実装）。

### 2.2 ケーブル一覧（**速度・長さ・完成数すべて暫定**）

| 種類 | 最大帯域 | 最大長 | コスト帯 |
| --- | ---: | ---: | --- |
| Cat5e LAN | 1 Gbps | 64ブロック | 低 |
| Cat6 LAN | 10 Gbps | 32ブロック | 低～中 |
| Cat6A LAN | 10 Gbps | 128ブロック | 中 |
| Cat8 LAN | 40 Gbps | 24ブロック | 高 |
| OM3 光ファイバー | 10 Gbps | 256ブロック | 中 |
| OM4 光ファイバー | 40 Gbps | 512ブロック | 高 |
| OS2 光ファイバー | 100 Gbps | 4,096ブロック | 非常に高 |
| 金星特殊光ファイバー | 400 Gbps | 8,192ブロック | 最高 |

現実の規格距離をそのまま再現する値ではなく**ゲーム用の初期案**。速度のGbpsはJava内部で扱う仮想ビットレートであり、実際のMinecraft通信帯域ではない。

クラフト数の暫定例：Cat5e 16個、Cat8 4個、金星特殊光2個。ネザースターを1ブロックごとに要求すると長距離配線が困難なので、希少素材は**光終端や高速ポート・回線設備**に重点配分する。

## 4. ポートごとの通信速度と拡張

### 4.1 設定（決定）

各ポート（例 `ge0/1`）は独立した**管理状態、物理規格、最大対応速度、Auto/固定速度、VLAN/Trunk、交渉済み速度、送受信統計、障害状態**を保持する。GUI/仮想CLIから速度を選べるが、そのポートが対応しない速度は設定不可。

リンクの上限は**自ポート、対向ポート、ケーブル、トランシーバー**の制約に従い、さらに**スイッチング容量／ルーター全体の処理能力**が共有ボトルネックになる。ポート専用スロットと本体共通スロットを分け、1ポートの強化は他ポートへ波及しない。

### 4.2 ポート速度モジュール（**暫定・1ポートの当該段階の追加消費**）

| 最大対応帯域 | 金インゴット換算 | 他の追加素材の例 |
| --- | ---: | --- |
| 1 Gbps | 標準装備 | なし |
| 10 Gbps | 16 | ダイヤモンド×2 |
| 40 Gbps | 64 | ダイヤモンド×8、ネザライトの欠片×4 |
| 100 Gbps | 256 | ネザライトインゴット×4、金星希少素材×16 |
| 400 Gbps | 1,024 | ネザライトインゴット×16、ネザースター×2、金星希少素材×64 |

**上位ほど追加素材自体が高価**。9マスのクラフト台に膨大なアイテムを詰めるのではなく、金ブロック、中間部品、独立したアップグレード作業台を利用する。Createの機械は必須にしない。

### 4.3 共通スロット（決定・スロット数は暫定）

| モジュール | 効果 |
| --- | --- |
| 耐久強化 | 内部ランダム故障率を50%低減 |
| 高度安定化 | 内部ランダム故障率を90%低減 |
| **完全安定化** | **内部ランダム故障率を厳密に0%** |
| 高速処理 | 本体の転送処理容量アップ |
| 大容量バッファ | 輻輳時の損失を軽減 |
| ポート増設 | 対応機器のポート数アップ |
| SFP系 | 指定ポートを適合する光規格にする |
| 冗長電源 | 電源系統故障を緩和 |

完全安定化は**内部ランダム故障だけ**に効く。ケーブル切断、停電、WAN設備障害、管理者による設定ミスなどの外因は防がない。速度強化と故障回避の選択に意味を持たせる。

## 5. 仮想インターネット・WANの段階強化

### 5.1 LANとWANの違い

- 同じLAN内の通信はWAN制限を受けない。**仮想ISP経由の別拠点通信は低帯域・遅延の制約**を受ける。
- 別VLAN間でルーティングしても、それだけではインターネット通信にはならない。**実際に仮想ISPを通る経路のみWAN制限**を適用する。
- ISP接続には回線契約・ONU等の設備・ルーターが必要。どの拠点が他拠点へ通信できるかは仮想公開IP、NAT、ACL、権限に従う。
- ISPや仮想Webの通信は**ゲームのシミュレーションのみ**。現実のLAN/外部サイトに接続しない。

### 5.2 WANアップグレード表（**暫定・前段階から追加で払う素材例**）

| 回線グレード | 最大WAN帯域 | 金インゴット換算 | 特殊素材 |
| --- | ---: | ---: | --- |
| 初期 | 20 Mbps | 0 | 基本装置 |
| 強化I | 100 Mbps | 32 | レッドストーン、クォーツ |
| 強化II | 1 Gbps | 256 | ダイヤモンド×16、ネザライトインゴット×2 |
| 強化III | 10 Gbps | 1,024 | ネザライトインゴット×8、金星希少素材×32 |
| 強化IV | 100 Gbps | 4,096 | ネザースター×2、金星希少素材×128 |
| **究極** | **400 Gbps** | **16,384** | **ネザースター×8、ネザライトインゴット×64、金星希少素材×512** |

- **1拠点の恒久強化**とし、日額料金等は設けない。究極WANは最高級LANと同じ**400 Gbps相当**の帯域まで向上する。遅延もグレードに合わせて短縮し、最終段階では体感がLANに近くなるようにする（遅延値は暫定）。
- 400 GbpsのWAN装置だけあっても、手前の1 Gbpsポートがボトルネックなら1 Gbps以下になる。
- 金インゴット「換算」は複数スタック、金ブロック、アップグレード専用中間部品として消費する総量であり、1回のクラフト入力数ではない。
- **金星素材は既存登録IDを実装時に検査**する。ニッケルや金星核・金星魂石等の採用候補はあるが、レシピに架空のアイテムIDを決め打ちしない。ボス進行に必須な素材の大量消費は入手導線も含めて調整する。

### 5.3 帯域割当・転送時間

通信の実効帯域上限は概念上**経路中の各ケーブル・両端ポート・機器処理容量・WAN契約容量・宛先NICの最小値**で決まる。混雑時はフロー間で共有し、優先順位やQoSで割当を変更できるようにする。

例: 10 Gbps PC → 1 Gbps L2ポート → 100 Mbps WAN → 10 Gbpsサーバーなら**100 Mbps以下**。

```text
仮想転送時間 ≈ データ量[byte] × 8 / 実効帯域[bps] + 遅延・キュー待ち
```

- G/Mの表記は10進SI接頭辞。実際に大容量のバイト列を生成せず、仮想データ量と残り転送量だけを管理。
- ファイル共有、物流、監視カメラ、サーバーバックアップ等に通信量を与え、帯域アップグレードを遊びに結びつける。
- WANでの帯域共有、混雑、損失はシミュレーション。無限に仮想パケットを発生させない。

| STP/RSTP | L2ループ抑止、ブロックポート、再収束 | 高 |

仮想CLIはJavaのパーサー。`ping`、`traceroute`、`nslookup`、`show mac address-table`、`show ip route`、`show ip ospf neighbor`、`show bgp`等を段階的にサポート。**OSのシェルコマンドを実行しない**。GUIとCLIは同じ設定モデルに対して作用する。

## 7. ランダム故障・修理・冗長化

### 7.1 故障ルール

故障は**ポート断、性能低下/パケットロス、機器全停止、モジュール異常**など。アイテム消滅やブロックの強制破壊は伴わない。修理キット/交換部品で直し、ランプ・GUI・Syslogに状態を表示する。**一度壊して再設置しても修理されない**。

| 難易度設定 | 機器単体の内部故障確率／ゲーム内1日（暫定） |
| --- | ---: |
| OFF | 0% |
| 低 | 0.01% |
| 標準 | 0.05% |
| 高 | 0.2% |

標準値では稼働機器100台の合計で、平均20ゲーム日（約6時間40分）に1件程度という概算。全機器の毎Tick乱数判定ではなく、**予約時刻によるイベント判定**を用いる。ロードされていない装置は原則停止させ、再ロード連打で故障判定を有利にリセットできないようにする。サーバー設定で無効化・倍率調整を可能にする。

### 7.2 冗長化

- **VRRP:** ルーター2台以上でゲートウェイの仮想IPを共有し、Masterの喪失時にBackupが引き継ぐ。Backup側にも有効な転送経路が必要。
- **STP/RSTP:** L2の冗長ケーブルによるループをブロックし、障害発生時に再収束させる。ブロードキャストストームも無限パケット生成で再現しない。
- **LACP/OSPF:** リンク束ね・動的ルーティングによる代替経路を用意する。
- 収束・切替のログを表示し、通信断時間はゲーム設定で緩和可能にする。完全安定化で単純化するか、モジュールを性能向上に回して冗長構成を作るかを選べるバランスにする。

## 8. PC・サーバー・Minecraftとの連携

PCに仮想Webブラウザー風GUIを用意する。`http://192.168.10.10/status`等の文字列はゲーム内仮想IP/ドメインの指定で、現実のURLへの接続ではない。Webサーバーは**MOD内で定義された安全なUIコンポーネントとデータ**を返す。自由なHTML/JavaScript/外部画像/任意コード実行を許可しない。

サーバーはLinux等を実際に起動せず、DHCP/DNS、仮想Web/API、ファイル、メール、監視、認証、Syslog、NTP、バックアップ等の**Javaサービス**を動かす。レッドストーン制御、ドア・照明、機械の遠隔操作、カメラ検知イベント、金星基地の生命維持・環境監視に利用する。切断時は「現状維持／停止／安全状態」を装置ごとに選択可能。カメラの映像は初期段階では低負荷の静止画像・イベントを優先する。

**マルチプレイの権限:** 所有者/チーム別の閲覧・設定・遠隔操作・回収をチェックし、GUI/CLI要求は必ずサーバーで権限・対象位置・データ長・レートを再検査。現実のPCのIPやシェルへのアクセスは不可。非公開の認証情報をクライアントへ無制限に同期しない。

## 9. 機器GUIとJEIによる説明

すべての機器に「状態」「ポート/ネットワーク設定」「拡張スロット」「障害・ログ」「ガイド」のタブを用意。ガイドには少なくとも以下を含める。

1. 機器の役割と通信原理（L2SWはMAC学習、ルーターは経路表など）。
2. **接続できる機器、対応ケーブル、ポート速度、必要素材**。
3. 構成図と手順（PC⇔L2SW⇔サーバー、ルーター2台のVRRP、スイッチ3台のSTP、ONU⇔OLT等）。
4. 各設定項目の意味、推奨値、通信できないときの診断方法。
5. 強化モジュールの効果と現在の速度ボトルネック・故障理由。
6. 対応済みプロトコル/コマンドと未対応機能。

JEI導入時は独自カテゴリ「接続・用途」「VLAN/ルーティング」「冗長化」「光回線」「サーバー」「強化」を登録し、構成図やレシピに加えCreateのガイドのように連携・使い方を説明。**JEIがなくても同内容を機器GUIから閲覧できる**よう説明を共通データで管理する。JEI/ Createへの必須依存は発生させない。

## 10. 機器破壊・再設置での保存

**決定:** 通常の採掘で、機器の永続情報を持つItemStackをドロップする（シルクタッチ不要）。再設置時に**設定・装着中の全アップグレード・スロットの中身・各ポートの速度・故障状態を復元**する。

| 情報 | 持ち運び時の扱い |
| --- | --- |
| ホスト名、固定IP、MAC、ルート、VLAN、ACL、OSPF/BGP/VRRP等の設定 | 保存・復元 |
| 各ポートの速度、ポートスロット、光モジュール | 保存・復元 |
| 本体拡張スロット、処理容量、契約済みWAN強化 | 保存・復元 |
| 故障/修理状態、所有者/チーム/アクセス権 | 保存・復元 |
| 動的ARP/MAC学習表、ルーティング隣接状態、稼働セッション | 再学習・再確立 |
| 世界に設置したケーブルの接続、Link Up、一時的な転送中フロー | 再接続が必要 |

NeoForge 1.21.1のBlockEntityとItemStack Data Componentsでバージョン付き永続化を想定。設定保存とアイテムドロップが重複してモジュールが増殖しないようにする。クリエイティブ複製等で**機器ID/MACが二重に稼働しない**よう再設置時にサーバーで重複をチェックする。認証秘密値は情報漏えいを防ぐためサーバー側の安全なデータ領域に分離可能。ただし実際の認証設定は再設置後も機能すること。

爆発等で機器アイテムがドロップする場合も同じデータを保持する。アイテム非生成の強制削除（奈落消滅や特定コマンド操作）まで自動復旧は保証しない。

## 11. 軽量化・チャンク処理・セキュリティ

- **ケーブルごとのTickerは禁止**。連続ケーブルを論理リンクとして管理し、変更時だけグラフ更新。不要な全世界走査をしない。
- サーバー側のJava仮想通信エンジンを、ブロック・描画・メニュー処理と分離する。プロトコルのタイマーはイベントスケジューラーで管理。
- 経路・MAC・ARPのキャッシュと変更時失効処理を実装。OSPF/VRRP/STPも必要な時刻・イベントだけ処理。
- 大容量通信は残り仮想バイト数・帯域配分・統計の数値処理。フロー、ログ、仮想パケットキュー、CLI操作数に上限を設ける。
- 過負荷時は仮想ネットワークに混雑・遅延・損失を反映して**MinecraftサーバーのTPSを優先**。
- GUI非表示時は細かい統計を同期しない。開いているクライアントへも変更差分を適切な頻度で送る。
- **チャンクを勝手に強制ロードしない**。未ロードの区間でも保存済み配線情報の参照は可能だが、アンロード済み端点機器・設備は原則停止扱い。
- 実ネットワークソケット、外部URL、OSシェル、ファイルシステム操作をMOD内の仮想通信から呼び出さない。
- ワールド保存・Data Componentには形式バージョンと容量制限を持たせる。クリエイティブ複製、サーバー再起動、チャンク再読み込みで整合性を維持。

**負荷計測候補（暫定・未測定）:** 100/500/1,000台の機器、1,000/5,000ブロック配線、100同時転送、複数人によるGUI操作、故障集中とSTP再収束、再起動。実測のTPS・メモリ・通信量で上限・更新間隔を決める。特定TPSを現時点で保証しない。

## 13. 受け入れテストと未決事項

**テスト項目（現時点すべて未実施）:**
- ケーブル種類、最大長、異種媒体、T字分岐、ポート交渉、MAC学習、ARP、pingの挙動が正しい。
- VLANを分けると通信不可、L3設定後は許可経路のみ通信可、DHCP/DNSは設定と結果が一致する。
- 高速なケーブルでも遅いポート・機器容量・WAN回線がボトルネックになる。ポート別強化が独立している。
- 初期WANはLANより遅く、究極WANは他の条件が揃ったときに最高級LANと同帯域になる。
- 故障・修理・完全安定化とVRRP/STP再収束が設定どおりに動く。
- 採掘後の設定・スロット・故障/権限が復元し、動的キャッシュは適切に再生成。複製IDは安全処理。
- 外部Web/OSへ通信できず、権限外操作、過大入力、通信キュー濫用を拒否する。
- JEIがない場合も機器ガイドを利用でき、導入時のJEIガイドと内容が一致する。
- 複数人、サーバー再起動、チャンクロード/アンロード、負荷集中でもTPSと保存データの整合を守る。

**具体的に実装前に決めること:** ケーブルの最終距離/レシピ/完成数、各機種のポート・スロット数、内部処理容量、金星素材の既存レジストリID、WANグレード別の追加遅延・契約方法、故障の細かな補正、ログ保持数、プロトコル/CLIの対応範囲、惑星間通信の詳細、性能目標値。
