# VRRP: 広告によるゲートウェイの冗長化

Minecraft 1.21.1 / NeoForge。以前の「問い合わせ時に最も高い優先度を即決する」実装を、**広告と期限によって各機器がMaster/Backupを決める方式**へ置き換えます。全体設計は [NETWORK_SYSTEM_SPEC.md](NETWORK_SYSTEM_SPEC.md)。今回もCreate/JEIは任意、現実のネットワークへ接続する機能ではありません。

## 基本の接続

```text
PC 10.0.1.10/24 ─ L2SW ─ Router-A P0 10.0.1.1/24
                  └─── Router-B P0 10.0.1.2/24
PCのゲートウェイ: 10.0.1.254
```

ケーブル区間は独立させ、T字分岐ではなくスイッチの別ポートから配線します。P0北/P1東/P2南/P3西/P4上/P5下。機器の正面を回しても番号は世界方位に固定です。

Router-A:

```text
port 0 ip 10.0.1.1/24
vrrp 10.0.1.254 150
vrrp port 0
vrrp group 1
```

Router-B:

```text
port 0 ip 10.0.1.2/24
vrrp 10.0.1.254 100
vrrp port 0
vrrp group 1
```

PCは `ip 10.0.1.10/24`、`gateway 10.0.1.254`。起動直後はまだMasterがいないので、VIPへのpingは成功しません。広告待ち時間を経て通常はAがMasterになります。**予備機から先のルーティング、対向端末の返信経路、ACLは別途必要**です。VRRPが勝手に経路を作るわけではありません。

## 確認・停止・復旧

```text
vrrp status
show vrrp
vrrp interval 2
vrrp preempt off
vrrp off
vrrp on
vrrp help
```

`vrrp status`は役割、VIP、VRID、優先度、担当ポート、広告間隔、送受信回数、期限までのtickと理由を表示します。閲覧ではタイマーを進めたり初期化したりしません。

`vrrp IP PRIORITY`は従来と同じ構文です。priorityは1〜254、VRIDは1〜255。`vrrp port auto`はVIPと同じサブネットの実IPポートが**一意**に特定できる場合だけ有効です。複数候補、別サブネット、ネットワーク/ブロードキャストアドレス、自身の実IPと同じVIPでは役割を担当しません。明示したポートが切れた場合に、勝手に別の面へ移ることもありません。

`vrrp off`はVIP等の設定を保持して停止します。Masterであれば優先度0の停止広告を送るため、Backupは通常の故障より早く引き継げます。`fault`・破壊・リンク断では停止広告を送らず、最後の広告からの期限満了を待ちます。修理キットで復旧します。

`preempt off`では、高優先度の機器が復旧しても、届いている現Masterの広告を尊重してBackupを維持します。`preempt on`では低優先度の広告で期限を延長しないため、期限後に切り戻します。同優先度の場合は、Master同士の広告比較で**実インターフェースIPの大きい側**が勝ちます。UUIDや設置順では決めません。

## 広告と切替時間

標準広告は1秒、設定範囲は1〜10秒。サーバーのゲームtickで進み、20tick=1秒として計算します。

```text
Skew = ceil((256 − 自機の優先度) × 受信広告間隔tick / 256)
Master Down = 3 × 受信広告間隔tick + Skew
```

例: 優先度100、広告1秒(20tick)ならSkewは13tick、Master Downは73tick。故障が起きてから常に73tickではなく、**最後に受け付けた広告から73tick**です。起動時は自機の設定間隔を使い、その後は受信したMasterの広告間隔へ追従します。優先度0の広告ではSkewだけを待ちます。実時間はサーバーTPSによって変わります。

タイマーは機器ごとに1件で更新します。毎回の広告受信で古い期限をキューへ積み上げません。状態変更はログへ記録し、周期広告ごとに大量のログを追加しません。

## 広告の遮断・競合とACL

広告は仮想のIPv4プロトコル`vrrp`、宛先224.0.0.18、TTL255です。実ソケットは使わず、既存のL2配線・VLAN・ポート状態と入出ACLを通過したメタデータだけを渡します。**L3ルーティングやNAT経由で広告を転送しません。** 受信TTL、VIP、VRID、送信元サブネット、優先度、広告間隔も検査します。

必要なACLの例:

```text
acl add 0 in 10 permit vrrp any any
acl add 0 in 20 permit ip any any
```

VRRPだけを止める試験:

```text
acl add 0 in 10 deny vrrp any any
acl add 0 in 20 permit ip any any
```

広告が届かなければ、それぞれの期限が満了して**二重Master**になることがあります。この状態を全体の優先度でこっそり解決せず、同じLANのVIPへ複数応答があった場合は競合エラーを返します。片方向だけの遮断でも発生し得ます。広告の復旧後は再び広告の比較で収束します。別VLANで独立した同じVIP/VRIDを使う構成は互いに影響しません。

MasterはVIPのARPに `00:00:5e:00:01:VRID` の仮想MACで応答し、切替後も同じ値を使います。現段階の基盤は経路メタデータのシミュレーションで、Ethernetフレームやgratuitous ARPの全ワイヤ形式を実装したものではありません。切替時にはMAC/ARPキャッシュを再学習させます。

## NAT・故障・設定保存

役割切替で稼働中の仮想転送とNAT変換表を失効させます。**NAT状態同期は未対応**で、古い接続を無損失に引き継ぐことは保証しません。予備機にも必要なNAT・ポート転送・ルート・ACLを設定して、新規通信を開始してください。NATの外側IPは従来どおり実ポートIPで、VRRP VIPをNAT公開IPとして使う拡張は今回含みません。

保存形式はv5。従来のVIP/優先度に加え、担当ポート、VRID、広告間隔、preempt、有効状態を、通常採掘でモジュール・故障・所有権と一緒に引き継ぎます。**役割、Master情報、期限、広告待ち行列は保存せず再確立**します。

v1〜v4を読み込めます。以前VIP未設定だった機器はVRRPを始めません。旧版で保存できた不適合なVIPも値は残し、他のACL/NAT/機器設定を捨てずにVRRPだけ稼働不可とします。古いMODへ戻す前提の互換性ではないため、更新前のワールドバックアップを残してください。

## 軽量化・制約・表示

有効機器128台、1機器の広告受信候補64台、広告配送キュー4096件、期限は機器ごとに1件、処理は最大64イベント/呼出しです。通常のサーバーは1tickごとに処理します。構成変更後のL2/ACL探索は2機器/tickに分割し、通常広告では結果を再利用します。上限超過は明示的に停止し、無制限に探索・キューを増やしません。

物理配線変更時は既存NetworkWorldがトポロジーを再作成するため、この段階ではVRRPも起動待ちから再開します。機器の故障フラグや設定の変更ではエンジンを維持し、変更のない機器のタイマーは残します。キャッシュ/転送失効は現在ディメンション単位で、無関係なネットワークにも影響し得ます。局所再計算・未ロード区間の中継は引き続き未実装です。

GUI/JEI共通ガイドにVRRP専用の5手順を追加しました。13トピック46手順。既存の機器アイコンを使い、ケーブル8種の4/16幅、PNG74枚、モデル、レシピは変更していません。

今回の範囲は**IPv4、1機器1VIP/1VRID、優先度1〜254、ゲーム内でVIP自体へのpingも受け付ける設定**です。IPv6、複数VIP、アドレスowner(優先度255)、認証、インターフェース追跡による優先度変更、NAT状態同期、ワイヤ形式/チェックサム/VRRPv2相互接続は未対応です。RFC9568の状態遷移を参考にしますが、実機互換の全機能を完成した扱いにはしません。

基礎資料: [RFC 9568](https://www.rfc-editor.org/rfc/rfc9568.html)。検証結果は [NETWORK_VRRP_VERIFICATION.md](NETWORK_VRRP_VERIFICATION.md) に記録します。
